# Studio Production Bootstrap

**Status:** implementation plan. No node installed, project created, or render queued.

**Decision:** add one V3 node, **Studio Production Bootstrap** (`StudioProductionBootstrap`, category `Studio/Production`), as the front door to a film. It previews a story breakdown and, on a separately approved run, creates the project scaffold. It does not generate media. Reuse Studio’s production validator, reference intake, Prompt Builder, H3/Hub, take tracking, and Brain; don’t install the five example nodes. The supplied Python returns hard-coded story data and blank tensors, not real generation.

## What the operator provides

| Input | v1 behavior |
|---|---|
| Story script | Required, multiline, verbatim. An incremental edit is not a new source unless the operator explicitly supplies a replacement. Preserve dialogue even when audio generation is deferred. |
| Project title, folder slug, project code | Require title and code; suggest a slug from the title and show it in Preview, with optional override. Slug is lowercase kebab-case; code matches existing `[A-Z0-9]{2,8}` grammar. Freeze both on creation. Code collisions are checked across Studio projects. |
| Delivery | Editable defaults: `16:9`, `24 fps`, `720p` delivery target. This is not H3 sampling resolution or a VRAM promise. Optional target total runtime; distinguish total scene duration, shot duration, and story time or timecode. |
| Audio intent | Default **silent draft**; alternatives: ambience only, dialogue planned. Keep source lines and sound cues. Under the current validator, a speaking character with no voice cannot produce a valid dialogue-bearing production document; ask for a voice definition or explicit text-only deferral. Never invent a voice or silently discard dialogue to get a green check. |
| Optional creative brief | Language, look/palette, camera preferences, intended audience or constraints, and known reference IDs. Leave absent facts unset in the proposal. Explicitly label defaults/proposals; don’t silently invent plot, props, likeness, or reference permissions. |
| Operation | `Preview` by default. `Create` takes the exact reviewed proposal ID/digest; no duplicate story entry is required as an implementation goal (reuse the frozen proposal). Headless callers need the same explicit Create contract. |

Show questions in the preview with the affected scene/shot and the reason. Do not ask the operator for dates/prefixes, sampler seeds, angles, model endpoints, credentials, model IDs, takes, or H3 continuation settings to create the scaffold. Optional rendering choices are supplied later via existing Studio presets and recipes. When required creative facts are missing, return `needs_input`, not invented canon or an invalid `production.json`.

## Flow and responsibilities

1. **Preview, no GPU on the ComfyUI queue.** A Studio service outside core owns intake. Reuse the local Qwen script worker (`studio/production_generate.py`) as a proposal engine, with 16K text context, fixed loopback and no cloud fallback. Also accept a prevalidated production document via Studio CLI for offline/deterministic workflows. The current local worker refuses to launch while ComfyUI listens; **v1 runs Qwen separately with ComfyUI stopped and loads the resulting local proposal after restarting through `.codex/launch.sh`**. Do not hide this limitation behind a node timeout, auto-stop the server, or spawn Qwen from `execute()`. Make an integrated one-click local proposal job a follow-on: it needs a verified scheduling/resource boundary with progress and cancel. Preview validates the proposal and shows the exact directory list, titles/IDs, scenes, shots, durations, reference needs, unresolved questions, and blockers. It writes no project files; proposal persistence, if required, uses local run state separate from the project tree.
2. **Normalize and validate.** Preserve `project.source_text`; use explicit source spans and validate offsets against the canonical source, not the model’s counts without checking. Bind/rewrite IDs deterministically across the proposal before validation; retain accepted IDs on revision, allocate new numbers without reusing deleted IDs, and show ambiguous entity matches for review. Reuse `studio/specs/production/production.schema.json` and `studio/production_validate.py`. Pin canonical source, proposal/plan digest, and schema version. `production.json` records authoring, not a graph or a render request. Validate local recipe compatibility separately; do not overload schema `target` with H3 if the existing enum cannot represent it. The backend selection belongs to reviewed recipe/bindings. Human accepts the breakdown; no image is approved here.
3. **Create a draft scaffold.** A deterministic Studio project writer is the sole filesystem owner. Validate project identifiers, resolve roots against the configured Studio/ComfyUI roots, reject symlinks/traversal/conflicting slugs or codes, stage in a sibling temporary directory and publish without overwriting. Approval binds to the exact proposal digest and approved destinations. Record created paths and project revision; reread manifest and hashes after publish. An identical repeat reports `already_created`; same ID with different content is a conflict (use explicit revision later). For multiple roots, publish the canonical project first and treat media dirs as lazy downstream-owned paths; no promise of cross-root atomicity. Do not delete stranded inputs or attempt to clean other projects. Creation is a deliberate output-node operation with tested execution/cache behavior, not an incidental side effect of loading, editing, or opening a canvas. Preview and Create do not submit any generation prompt.
4. **Plan references from the real entities and shots.** Deterministic task list from the accepted document. Character face/identity, wardrobe, location, prop and composed shot frame are distinct roles. A turnaround is an optional request, not a required sheet: keep views individually and use contact sheets for review. Start/end frames are explicit shot constraints; use an end frame only when needed. Missing/duplicate/unapproved references remain review tasks; reuse `asset_intake.py` and human approval, preserving bytes and hashes. No invented file paths, model downloads, or placeholders that look like ready assets. Follow [Reference strategy](../docs/REFERENCE_STRATEGY.md).
5. **Hand off to existing production tools.** Fill reviewed assets and shot bindings, choose recipe and transition, derive prompt from the authored shot data via the existing compiler/Prompt Builder, then run model/asset/graph/resource preflight. Suite Hub owns its runtime project and creates it only when deliberately opening a rendering flow. Use a browser-compiled graph and freeze prompt/package, model refs, output paths and seed with the existing take tools. Brain observes actual runs and reports evidence; it is not the planning registry and does not approve creative output. Nothing renders automatically after scaffold creation.

## Layout and named contracts

| Path | Owner and contents |
|---|---|
| `studio/projects/<slug>/project.json` | Proposed small bootstrap manifest: version, stable slug/code/title, source revision/digest, schema version, approved proposal digest, delivery choices, project-relative artifact paths. No duplicated shot/asset bodies, no credentials, no absolute workstation paths. |
| `story/script-v001.md`, `production.json` under that directory | Exact source and accepted existing-schema breakdown. `project.source_text` stays identical to the source; verify that invariant on read. Later revisions preserve the prior accepted source/plan without rewriting existing take data. |
| `assets.json`, `bindings.json`, `shot_transitions.json` under that directory | Existing contracts: empty asset registry is valid for a draft; only reviewed bindings use real asset IDs. If `bindings.json` is kept empty at scaffold time, do not call `film.compile_project` until the readiness gate confirms every requested shot has a binding. Use `cut` for an independent first draft; continuation and start/end frames are explicit. |
| `reference-plan.json` under that directory | A local checklist/report keyed by existing entity/shot IDs, not another asset registry. Record role, subject, shot dependency and missing/available/needs-review status; final asset facts live in `assets.json`. Avoid a separate naming-registry node. |
| `input/refs/<slug>/` | Reference bytes filed by reviewed intake as needed. Keep existing path conventions and deterministic naming; date belongs in provenance, not the identifier. |
| `user/master_studio/…`, `output/<namespace>/shots/<shot>/<take>/video`, `output/h3_projects/<suite-name>/…` | Keep existing take, delivery and Suite ownership. Introduce no second copy of media, runs DB, or H3 state. Resolve one stable output namespace; do not inherit `The_Message` for new films. `models.json` and recipe pins are created only when selected and verified. |

Example keys for **Midnight Compass** (`midnight-compass`, `MC`): `MC-CHR-KAEL`, `MC-PRP-BRASS-COMPASS`, `MC-LOC-NIGHT-MARKET`, scene `MC_S001`, shots `MC_S001_SH01` and `MC_S001_SH02`. A proposed wide establishing shot and close-up can share the same wardrobe and prop references; neither needs a rendered turnaround to exist. Treat `00:00:12` as ambiguous until confirmed (scene duration or script timecode), and the quoted line as authored dialogue needing a voice decision or explicit silent-draft deferral. Preserve the rain and vendor cues as notes, not created audio. Use `v001` for script revisions and existing take naming (`tk001`, etc.) at the take stage. Never derive identity from filenames, calendar dates, or display labels.

## Implementation slices and acceptance gates

1. **Contract first:** add the small manifest and proposal contract, CLI preview/create, and fixtures for the compass scene plus a no-dialogue scene, reused cast/locations and ambiguous duration. Keep draft vs render readiness explicit (`needs_input` → `preview_ready` → `scaffold_created`; separate render readiness). Test schema/spans/source fidelity, stable/colliding IDs, missing voices, blocked references, traversal/symlink/concurrent creates, interrupted staging, no-clobber and identical replay. Use fixed offline fixtures before a real local-Qwen test; compare questions and source fidelity, not narrative creativity.
2. **Thin V3 UI adapter:** validated file selector or typed proposal input, compact read-only preview summary, explicit Create confirmation. Use existing resolvers and check containment again at write/read boundaries. Return only the bootstrap-owned project handle or manifest ID and readable report; no `IMAGE`, video, raw endpoints/keys or pass-through sockets. Keep the node in local Studio integration/custom-node code, not `comfy/`, and keep the deterministic service usable without a running GUI. Verify from a scratch canvas via the visible browser, including a double-run, with no generation queued. Node execution may use the normal queue to execute the CPU-only bootstrap operation; distinguish that from dispatching a render.
3. **Remove the Master Studio handoff blocker:** `studio/master_studio_package.py` currently hard-codes The Message paths, output naming and `PROMPT_FILES` by shot. Add a narrow project-aware selector/resolver keyed by manifest + shot ID, keeping current legacy canvas behavior intact and adapting existing prompt/media/RefMod libraries rather than rewriting them. Preserve package/take contracts. Test two independent projects resolving without cross-talk, verify actual compiled canvas inputs and frozen package hashes before any authorized render, and show missing assets as expected blockers. A draft created successfully is not proof the new project can render.
4. **Pilot one simple project:** scaffold the multi-location outline below, then qualify only one representative scene and one or two shots first. Prepare a small reference set and authorize one short representative take only after preflight and queue/resource checks. Verify media hashes, actual node bindings, native history, Suite files and Brain run separately from visual acceptance. Stop once the end-to-end handoff is proven. Full automated story/video generation, cast sheets for every angle, batch rendering, transitions beyond basic cuts, voice cloning, assembly, multi-user permissions and training are not v1 requirements.

## Pilot refinement: location references first, short shots second

Use the **man, woman, plane, horse and island** story as the first simple pilot. Break the script into story beats and distinct places before proposing coverage. A beat is not automatically a shot, and a place is not automatically a new asset on every cut. Reuse a location ID when the story returns to the same place, with separate views or lighting variants only when needed.

| Authored beat | Reference needed before shot planning | First coverage proposal |
|---|---|---|
| Man meets woman; they fall in love | Both identities and wardrobes; the meeting location is unspecified | One meeting action per clip; an optional separate reaction or later moment can show the relationship developing. Ask what visible action should communicate it. |
| Woman boards a plane for the island | Departure location or boarding area; plane exterior if visible; keep her wardrobe/accessories consistent | One boarding action. Add a cabin or takeoff shot only if the user wants to show it; each would create its own reference need. |
| Man rides toward the island | Horse, riding wardrobe, departure location; ask how the route reaches the island | Separate mounting and riding if both are shown. Do not invent a bridge, ferry, or any other crossing. |
| Island destination | Island location and arrival viewpoint, once selected | Establish the destination if the script calls for it. Do not infer a reunion or design an arrival route from the outline. |

In the preview, show an ordered **Location → Scene → Shot** checklist and a small reference slate per shot. Mark each reference `missing`, `candidate`, or `approved for input`, independently of creative approval. Start with one clear establishing view per needed location, then add a reverse or exact composed frame only when it changes the shot. Reference creation is a separate approved step using existing still workflows and intake; the scaffold only creates the checklist, not empty images masquerading as assets. Once references are selected, assign each one an explicit role and verify the actual encoder mapping.

**Short-clip rule for the first pilot:** plan one visible action and one camera move per shot, target 3–4 seconds, and use about 5 seconds as the maximum **delivered** clip budget for this workstation pilot, not a model limit. Split longer beats into coverage and use independent cuts by default. Keep story time, planned clip duration, and H3 raw/delivered frame counts separate. Check the existing `master_studio_compiler.plan_frames()` at handoff: alignment and continuation can change raw and delivered lengths; flag drafts above the agreed delivery budget instead of silently rounding them upward or adding tail context.

### Preserve the existing Fantastic and Project Suite contracts

- **Fantastic H3 Prompt Builder:** Master Studio’s shot resolver drives `MiniMaxH3PromptBuilder`, `MiniMaxH3MediaLoader`, `MiniMaxH3RefModStack` and the CPU Reference Map. Keep the committed prompt text and structured editor state together, with the selected project and shot binding. Bootstrap proposes shot facts (subject/action, location, composition, camera/light/audio intent) and reference roles, not a replacement prompt string. On REF handoff, preserve the Builder’s enabled sections and `[Shot 1]` opening; derive `<Picture N>`/`<Video N>`/`<Audio N>` only from actual media binding, not storyboard order. Use `studio/prompt_review.py` to check section structure, text/state parity where supported, subject retention, conflicting camera instructions, and citations against the real map. For a composed first frame or first/last frames, choose a compatible model/recipe explicitly and use that Builder mode rather than pretending every shot is REF.
- **Fantastic LoRA:** Keep `FantasticLoraLoaderMulti` and `FantasticLoraMimicSubgraphCompanion` in the existing model/LoRA rig. A new scaffold does not select, enable, download or train LoRAs. A reviewed render preset may pin a compatible stack, enabled flags, order and strengths. Keep that separate from the RefMod picks and reference stills. For the pilot inherit only an explicitly reviewed baseline (no new LoRA enabled by default), and record the actual stack with the frozen take. The LoRA lab stays muted.
- **Project Builder / H3 Project Hub:** Keep Studio’s planned film and the Suite’s runtime project separate. Pass the reviewed stable project/namespace, shot selection, frame plan and transition into the existing resolver/Hub arrangement. The first independent shot consumes no context tail; only a later explicitly continued shot uses an approved prior clip. Verify new-project routing without overwriting The Message’s prompt/media libraries, Hub name or outputs. A CPU-only pilot acceptance check should open a scratch shot in the existing Builder, round-trip its state/text, show the reference map from approved inputs, and verify the Hub target and inherited LoRA state without queueing a render.

### Inline hints and frame choices

- Use short hints beside the controls, not extra required fields. **Shot**: “One visible action per clip. Start with `[Shot 1]`.” **Subject**: “Choose an existing character or prop. The Builder inserts `<Subject 1>` and binds the selected reference.” **Camera**: “Pick one movement, or keep it static.” `Camera` is a UI label, not a new `[Camera]` token; use the existing Builder insertion control. Keep the numeric spacing and bracket types used by the Builder, and do not confuse `[Shot 1]` inside a clip prompt with the project’s stable shot ID.
- **First frame — What should the shot open on?** For a planned action, default to proposing a composed still that establishes the actual framing, pose and prop placement. Keep the separate identity/wardrobe/location/prop stills in the reference bank. Bind the approved composed still to the selected FL2VA recipe’s actual `first_frame` input; an ordinary REF picture is not that input.
- **End frame — Does the shot have to land on a specific pose or composition?** Optional, off by default. Show it only for an endpoint-capable recipe; bind it to `last_frame` when explicitly selected. Check it against the first frame for continuity and intended changes. An end-frame constraint is not a guarantee of the motion between them. It is also not automatically the next clip’s start frame or an approved Hub continuation tail.
- Show `not needed`, `missing`, `candidate`, or `approved for input` for each applicable frame slot. Before rendering, show which file and role reach the actual inputs. Reuse the [reference strategy](../docs/REFERENCE_STRATEGY.md): the kitchen test improved object continuity with a composed first frame but missed the intended low lift; first-plus-last is supported, not proven better in a controlled comparison.

**Done for v1:** the user can turn a short story into an approved, non-overwriting project scaffold, see what references and decisions are missing, and open it in Master Studio without touching The Message. Rendering still requires a separate explicit action and approval gates.
